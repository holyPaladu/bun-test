# Документация проекта

Этот каталог содержит только действующие документы. Завершённые планы
рефакторинга и описания прежнего состояния удаляются: историю изменений следует
искать в Git, а не использовать как руководство к работе.

## С чего начать

Если вопрос — **«что писать следующим?»**, читать в таком порядке:

1. [Roadmap платформы](roadmap.md) — очередь работ и критерии перехода между
   этапами.
2. [План auth-service](services/auth-service-roadmap.md) — что исправить в
   существующей аутентификации.
3. [TODO auth-service](services/todo/auth-service-todo.md) — конкретные чекбоксы,
   файлы и команды для начала работы.
4. [План user-service](services/user-service-roadmap.md) — что исправить в
   существующем сервисе профилей.
5. [План finance-core](services/finance-core-plan.md) — какой новый сервис
   создавать, какие модули в него входят и что составляет первый slice.
6. [Проверки проекта](quality-gates.md) — какую команду запускать, что именно она
   доказывает и какие проверки пока отсутствуют.

Если нужно сначала понять **«что мы строим и почему?»**, начать с
[видения продукта](product/fintech-platform.md), затем прочитать roadmap.

Короткий ответ на текущем этапе: не создавать отдельные `organization-service`,
`payment-service` и `ledger-service`. Сначала закрыть foundation в
`auth-service` и `user-service`, затем создать один `finance-core` как модульный
монолит. Границы модулей внутри него сохранят возможность выделить сервис позже,
если появится измеренная причина.

README сервиса описывает то, что существует сейчас. Roadmap описывает будущую
работу. Документ со словом «план» не должен после реализации оставаться вторым,
конкурирующим источником истины.

## Как читать статусы задач

- **Реализовано** — возможность найдена в коде и для неё есть хотя бы одна
  воспроизводимая проверка.
- **Частично** — код или тест уже есть, но отсутствует обязательный quality gate,
  эксплуатационная часть либо зафиксированный контракт.
- **Не реализовано** — это следующая работа, а не обещание текущего сервиса.
- **Отложено** — задача сознательно не нужна для ближайшего результата.

Дата проверки относится только к снимку репозитория на эту дату. Источником
истины для текущего API остаются код и сгенерированный OpenAPI, а результаты
команд фиксируются в [документе проверок](quality-gates.md).

## Как поддерживать документацию

- При изменении публичного API обновлять OpenAPI и README сервиса в том же PR.
- При выполнении roadmap-задачи переносить итоговое поведение в README/стандарт,
  а задачу удалять или явно помечать выполненной; не оставлять её как будущую.
- При добавлении сервиса обновлять карту в `docs/roadmap.md`, его README и общий
  набор проверок. При добавлении модуля внутри `finance-core` новый сервис в
  карте не создавать.
- Архитектурное решение с долгим сроком жизни оформлять как ADR: контекст,
  решение, последствия и критерий пересмотра.
- Не помечать предположение как реализованную возможность.
- Не копировать большие куски одной и той же информации в несколько файлов;
  давать ссылку на канонический документ.
- Завершённый migration/refactoring plan удалять после переноса сохраняемых
  правил в действующий стандарт или README.
